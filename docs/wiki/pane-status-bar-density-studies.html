Pane & Status Bar Density Studies

Design study (260914 discussion) for the two desktop register surfaces the user reads together: the sidebar PANE section (sidebar/status-panel.tsx) and the shell-level status bar (components/status-bar.tsx). Both were read as "too congested" on a 1512 px MacBook viewport with the PANE section opted in. The study annotates the screenshot state, inventories where every datum appears, budgets the text against the real widths, and proposes changes per surface with a live fold mock. Authorities it builds on: docs/specs/status-pyramid.md § Row Minimalism (the five registers stay orthogonal — decided), status-signals.md § Status Bar (the degradation ladder), and the flyout card's continuation lines rather than truncation decision.

When the branch does not carry the change (here main, or a hand-named t7vy-launch), the fab row keeps its slug — the slug appears exactly once either way. This is also where the rule becomes a signal: a fab row with a slug beside a branch row means "this pane is not on its change branch" — the exact situation the git-pr branch-guard trips on.
  • atmx shows the pane id, and the index only when it disambiguates. %107 alone for a single-pane window; %107 · 2/3 for multi-pane, with tmux's index verbatim (fixes the off-by-one at the source — the bar and the overflow menu row share the string). Copy value stays %107.
  • bcwd is basename-first; the parent yields. The basename is shrink-0 in primary ink, the parent path is dim and truncates from its head (a direction: rtl span holding an isolated bdi — no JS measuring). At any width the row ends in the worktree name. Copy stays the full path; the tooltip stays the full path.
  • cgit dims the date prefix when the branch matches the change pattern (^\d{6}-). It is a purely visual de-emphasis so the eye lands on png4-compose-default-on; the copy is still the whole branch.
  • dfab drops the slug when the branch already carries it — png4 · review-pr · active. The rule lives in the shared resolver (getFabLine(win, branch) in sidebar/registers.ts) so the PANE section, the flyout card, and the bar cannot disagree: if the active pane's branch ends with <id>-<slug>, omit the slug. This is also what the spec's own register example shows — fab 260705-dmex · review · failed has no slug. The displayState gets its fab-hue colour (green active / yellow ready / red failed) as the dot does, so the row reads as state, not prose.
  • eout stops narrating. active · claude → claude · flowing; claude — idle 4m since last output → claude · idle 4m. The tier-1 tip (Output activity) already says what the elapsed means. Command first because that is the stable token; the state word varies. "flowing" is proposed over "active" so L0 and L1 stop using the same word for different things (bytes vs. intent) — this is the one vocabulary change and it is UI-only (no hook or tmux option changes; activity: "active"|"idle" stays the wire value).

C3 · Continuation instead of truncation for long registers

Even after the diet, an open PR row (#971 · open · checks pass · review: approved, 42 chars) overflows 22. The flyout card already decided continuation lines rather than truncation for exactly this register; the PANE section can adopt the same rule for pr and fab: the decisive tokens on the key line, the rest on a dim continuation indented under the value column. A row never exceeds two lines; the third and later segments truncate as today.

Cost: the panel grows by one line per PR with checks. It is the opt-in detail surface; growth there is the right trade. The bar (a one-line strip) never wraps — it folds (§ D1).

C4 · Kept as is, deliberately

  • Five orthogonal registers. Collapsing out/agt/fab into one status line was rejected in the spec (Row Minimalism, decided): the dot must stay mentally derivable from the rows. The perceived triple "active" is fixed by vocabulary (§ C1 e), not by merging.
  • The PANE header's dot + name. It is the only status that survives collapse, and the panel is bottom-aligned while the selected row may be scrolled out of view. The duplicate with the row directly above is the cost of that guarantee.
  • The refresh button. Server-global PR refresh; unchanged.

D · Proposals — the status bar

D1 · A measured priority fold replaces the breakpoint ladder

The bar's ladder is viewport-keyed (xl/lg/md/700) while its content is value-keyed: whether the strip fits depends on how long this window's branch and fab line are, not on how wide the window is. The project already has two measured folds that solve exactly this: the top bar's crumb collapse (ResizeObserver + a hidden probe row, top-bar.tsx) and the gui tile's header toolbar (lib/gui-toolbar-fold.ts — a priority ladder with a two-pass reserve and an overflow menu). The proposal reuses the gui fold's shape for the bar:

  • Every segment renders at natural width or not at all. Truncation is reserved for the single lowest-priority survivor when even the fold cannot make room (the top-bar crumb rule), so the branch, the PR, and the identity fragments are always either complete or in the … menu — never runK….
  • Fold order (dies first → last), one list across both clusters so the two sides stop competing: ld → ⌘K · a▏ hints → cwd → tmx → ◷ next-fire → server (the top-bar breadcrumb carries it) → cpu · mem → version → agt → ⑂ branch (when it equals the change branch: the fab id + the folded branch are one identity) → host → fab slug (already gone when the branch carries it) → never: pr, fab id · stage · state, the stale ◷, the connection dot.
  • The … menu is the fold's overflow, listing exactly the folded segments in strip order with the same copy/open actions — the existing menu, fed by the fold state instead of inverse breakpoint classes. Display order in the strip stays branch-first (decided); only the survival order changes from "rightmost dies first" to the explicit ladder above.
  • Collapse-first, reflow-free (the gui fold's rule): the fold state starts collapsed and expands after the first measurement, so the bar never paints a wide frame then snaps. Values that change length every second are already gone from the bar (out left in 499u), so the fold recomputes on window switch and on resize, not on a clock.

D4 · When the PANE section is on, the bar's window cluster yields

The bar's left cluster exists because the desktop PANE panel was retired; the panel is opt-in so the bar can be the only copy. The missing half of that contract: when a desktop viewer opts the panel back in, the bar hands the window registers back to it and keeps only the host cluster (plus the never-drop pr segment — the one register with an action the panel does not sit next to). One prop seam: Shell already knows showPane from the section-visibility rail; it passes window={null} to StatusBar when the panel is visible on desktop. The user then has two coherent modes instead of two half-truncated copies:

  • Panel off (default): the bar is the compact register view, folded to fit.
  • Panel on: the sidebar is the register view with continuation lines; the bar is host chrome. The left half of the bar goes quiet, and the right cluster stops folding at all normal widths.

Toggle PANE section on in the toolbar to see the third bar in § D2 switch between the two.

D5 · Three stacked bars

Above the compose strip sits the tmux status line — a window list the sidebar already renders, plus a session name and a clock. It is tmux's chrome, not ours, and the drawer study parked hiding it for the operator session (row 6, "session-wide side effect": status is a session option, so a local tmux attach to the same session loses the bar too). The same trade generalises: a tmux.status setting (on default · off) applied through the managed tmux.conf to @rk_srv_managed servers would remove the third bar for people who only ever view through the web. It stays parked here as well: it is outside the two surfaces the study was asked about, and it is a per-user preference rather than a density fix. Noted because the eye counts it.

Rejected

  • Collapse the five registers into one status line in the panel or the bar. Spec § Row Minimalism (decided): the dot must be derivable from the rows; a single line re-creates the "what does this dot mean" problem the registers solved.
  • A settings surface for which bar segments show. Constitution IV allows one registry-driven settings surface and VII prefers convention; a priority fold is the convention. A per-segment picker is the kind of configuration the fold makes unnecessary.
  • Horizontal scroll or a two-row bar. The ladder's own rule — never scroll — and a 24 px VS-Code-class strip is the frame; two rows is a panel, and the panel exists.
  • Drop the git row from the panel when the branch equals the change. Cheaper than the slug rule, but it takes away the one row people copy most (the branch) and turns a status surface into an inference exercise. Dimming the date prefix and moving the slug out of fab keeps the copy target and still writes the slug once.
  • Hide the bar's left cluster whenever the sidebar is open. Too aggressive: the default desktop has the sidebar open and the panel off, and the bar is then the only register view. The yield is keyed to the PANE section, not the sidebar.
  • Rename the agent-state vocabulary (active → working) to break the triple "active". The values are written by the harness hooks and read cross-repo (agent-state.md); the L0 word is ours to change, the L1 word is not.
